# Architecture

## Objective

The repository is a compiler-like TypeScript-to-Rust translation system:

```text
upstream revision
  + generator revision
  + target configuration
  + semantic mappings
  = reproducible Rust crates
```

Handwritten Rust implementations and direct edits under `generated/` are not sources of truth.

## Pipeline

```text
Flight package barrels and TypeScript sources
                    ↓
       TypeScript AST and export graph
                    ↓
       normalized language-neutral IR
                    ↓
      Rust ownership and type lowering
                    ↓
      deterministic modules and crates
                    ↓
        rustfmt, cargo check, and tests
```

The inventory covers every upstream package regardless of current Rust emission support. The generation report separately identifies translated, mapped, and unsupported sources.

Upstream conformance is harvested from pinned TypeScript test ASTs rather than copied into handwritten Rust fixtures. Translation attempts are file-scoped and configured: generated Rust assertions are attached to the corresponding automatic candidate, and generation runs them before recording them as passing. Only a completely translated file increments file coverage; unselected or partially translated in-scope files remain explicit fingerprinted unsupported entries with a reason. The headline metric is translated-and-passing upstream test files over all inventoried upstream test files; generated assertion counts are reported separately so a large file cannot masquerade as broad package coverage.

## Rust API

- `@flighthq/<name>` maps to crate `flighthq-<name>`, except for the explicitly temporary cultivated bitmap compatibility alias documented below.
- Defining TypeScript files map to snake_case Rust modules.
- Exported camelCase free functions map deterministically to snake_case free functions.
- Allocation, teardown, sentinel, out-parameter, and aliasing vocabulary remains explicit.
- Target-specific capabilities sit behind maintained runtime seams rather than contaminating bulk generated code.

## Blessed facades

`packages/surface-rs` is the compatibility-named cultivated TypeScript/wasm facade for upstream `@flighthq/bitmap`, and the bitmap source/declaration admission policy is maintained explicitly. The `flighthq-surface` pixel kernels are generated from those selections and carry generated provenance; they are not a handwritten Rust boundary. This facade is the only package intended to ship as a standalone wasm package. Retaining `flighthq-surface` preserves the existing shipped facade during the upstream surface-to-bitmap migration; it is a recorded crate-naming exception, not a second canonical identity for `@flighthq/bitmap`.

Cultivation is opt-in and package-specific. The bitmap policy's `cultivated` disposition describes its maintained facade and admission selection, not the authorship of its generated Rust crate. Every other substrate-neutral package remains generated by default, while build tools, `*-dom` packages, and host adapters are governed by explicit policy.

## Native host boundary

Native hosts are cultivated adapters over generated package seams; they are not translations of the web default backend. The cultivated `flighthq-host-winit` compile canary installs generated application, lifecycle, keyboard, haptics, power, screen, platform, and device backends as one bundle and creates the generated input manager. Its concrete event-loop and rendering adapters remain handwritten host work.

Global TypeScript `Promise<T>` types lower to target-neutral task IR; a source-declared type that merely has the same name remains nominal. Every async scope and task-valued construction carries stable source identity and is partitioned as executable, configured host placeholder, or unsupported. The generated `flighthq-runtime` supplies the one canonical `FlightTask<T>` identity to candidate, promoted, host, and wasm graphs. Typed ready/reject and straight-line async/await execute through an explicit scheduler seam; generated tests install the deterministic scheduler automatically. Dynamic outputs and task sources that still require `OpaqueHostValue` remain distinct blockers, and unsupported composition never falls back to a default task. The Pass 27 [Future/task IR design](future-task-ir.md) records scheduling, ownership, error, and later-stage gates.

Current native-host prerequisite frontier:

- lifecycle, keyboard, haptics, platform, and device compile as automatic candidates; generated partial application, input, power, signal-constructor, and screen seams retain the host canary while their unresolved automatic task paths remain explicit blockers;
- the host-winit canary compiles those seams together in its own Cargo workspace;
- the render stack waits on log plus the node/material/skeleton dependency frontier;
- candidate and promoted crates share dependencies through the dependency-closed promotion model below;
- concrete winit event translation and renderer ownership are the next cultivated host steps.

## Crate identity across promotion

Every `@flighthq/<name>` package has one Rust package identity, `flighthq-<name>`, in a compilation graph. Promotion does not rename crates, and candidate crates do not receive a distinct prefix: either approach would turn source-compatible Flight types into nominally different Rust types and require adapters at every mixed-graph boundary.

Promotion is therefore dependency-closed over the emitted Rust graph. A package may become fully promoted only after each Flight package referenced by its emitted crate is fully promoted. Manifest-only dependencies do not create a Cargo identity edge: upstream may isolate opt-in guard or debugging modules from the generated surface even though `package.json` must declare their dependencies. Full promotion is explicit target configuration, never inferred from an empty selection, and may carry a source-level exclusion only when the target records why that module is outside the always-loaded portable surface. Source or declaration selections remain partial targets. A partial cultivated target does not own the package identity in the automatic candidate graph. Generation must reject a fully promoted target whose emitted dependency closure contains a partial target or automatic candidate.

The candidate graph resolves each package through one deterministic map:

1. A fully promoted package resolves to its crate under `generated/crates`.
2. Every other generated package resolves to its crate under `generated/candidates`.
3. Only the second group is a candidate-workspace member; dependencies may point at the first group as external path dependencies.
4. Generation rejects duplicate package identities and any emitted dependency edge that disagrees with the map.

This merges the graphs incrementally as packages graduate without maintaining graph-specific copies. For the current `types`/`easing`/`tween` boundary, `@flighthq/types` must graduate from its partial target to the full already-compiling package before the fully promoted `@flighthq/easing` crate can enter the candidate graph. `@flighthq/tween` and its automatic `@flighthq/signals` dependency then both resolve `flighthq-types` to that promoted crate, while emitted easing imports reach the same path. Cargo sees one `flighthq-types` identity throughout the graph.

Two workspaces are the intended end state, not a temporary omission. The root workspace tests promoted shipping crates, while the generated candidate workspace separately checks the automatic graph and executes admitted generated upstream conformance modules. `cargo test --workspace` covers only the root; `npm run ci` must continue to check both graphs through deterministic generation/candidate compilation and conformance execution followed by root-workspace and host tests.

`@flighthq/image` is the deliberate permanent partial exception. Its promoted crate admits the portable image-resource state slice, while `imageResourceFrom.ts` browser element/load/decode behavior remains host-bound. The automatic candidate and promoted partial crates may therefore keep the same `flighthq-image` package name in their separate workspaces, but the resolution map must never admit both paths to one Cargo graph. This model mitigates cross-graph X1 collisions; it does not claim that duplicate package names disappear globally. Full promotion of image would violate the host boundary and is forbidden unless that policy itself changes.

The compatibility-named `flighthq-surface` crate is the one temporary X1 naming exception. It is a partial generated selection from `@flighthq/bitmap`, not the automatic package candidate, while the inventory reserves `flighthq-bitmap` as that upstream package's canonical crate identity. The exception is safe only while `@flighthq/bitmap` remains `cultivated`/not-applicable: no automatic `flighthq-bitmap` candidate may enter a Cargo graph containing the selected `flighthq-surface` definitions. This preserves the shipped `@flighthq/surface-rs` wasm facade without pretending the compatibility name follows the normal package mapping.

The migration path is explicit:

1. Generate the admitted bitmap kernels under canonical crate `flighthq-bitmap`, without changing their source/declaration selection.
2. Change `flighthq-surface-wasm`, maintained templates, tests, and workspace manifests to consume `flighthq-bitmap` directly. If compatibility requires the Rust name to survive, replace `flighthq-surface` with a thin re-export adapter; it must not contain a second generated copy of bitmap types or functions.
3. Remove this exception only after the wasm artifact, surface parity suite, root workspace, and downstream imports pass with the canonical crate. Reconsider automatic bitmap candidacy only after the compatibility-generated definitions can no longer coexist with it.

Fully promoting `@flighthq/types` expands the root workspace and blessed wasm dependency from its curated slice to the complete generated type package. That transition is allowed only while `npm run wasm`, the `packages/surface-rs` parity suite, and `cargo test --workspace` all pass. A new dependency that the wasm target cannot satisfy blocks the promotion even if the automatic candidate graph compiles.

## Generator blocker architecture

The compiler-driven candidate matrix classifies work in dependency order:

1. Source blockers identify missing AST/IR language features or incomplete barrel/export synthesis.
2. Compile blockers identify Rust type, ownership, representation, or control-flow defects after emission.
3. Dependency blockers are not patched locally; they automatically re-enter compilation when prerequisites compile.
4. Host-bound operations lower only through explicit placeholders or cultivated backend interfaces.

Canvas, WebGL, and WebGPU packages carry an explicit `host-backend` disposition while typed backend-capability IR remains outstanding. Existing opaque sources in substrate-neutral packages are grandfathered by a per-package baseline that may decrease but not grow; a baseline overage produces source-scoped emission blockers rather than new `OpaqueHostValue` output.

Structural records are interned by resolved schema at module signatures, preserve imported nested-record provenance, and project across nominal Rust records with single-evaluation ownership. Ordered object-field emission clones a directly consumed non-`Copy` local when a later field still references it, including when distinct source aliases share one Rust representation. Generic projections use Rust constructor turbofish syntax and never capture unbound type parameters in a module-global record.

The Rust target owns representation-driven semantics that should remain explicit when the generic IR moves to `flight-compiler`. Non-`Copy` values are cloned from consumption liveness across ordered fields, sequential statements, loop back-edges, and switch discriminants, rather than from source alias identity. Mutating JavaScript collection methods that return their receiver mutate an addressable Rust place and return an owned clone, while temporary receivers stay owned and are returned directly. Indexed string algorithms materialize one UTF-16 view per reused string parameter so JavaScript `.length` and `codePointAt` share code-unit indexing without repeated UTF-8 scans; `codePointAt` retains surrogate-pair and trailing-surrogate behavior. Nullable conditional joins produce `Option` at each branch, a contextually non-null indexed read unwraps only when its inner semantic type matches the target, computed Copy scalars stored in `LazyLock` are dereferenced at reads, and numeric bitwise-not applies JavaScript `ToInt32` without disturbing nominal Rust bitflag enums.

Automatic candidates also own one Cargo identity per upstream package, independent of any differently named partial cultivated crate used by a host seam. Flight public subpaths resolve declarations through the owning package root so indexed-access types do not collapse to the dynamic boundary. A task obtained from a dynamic host call is represented by a typed `HostUnavailable` rejection; this requires no `Default` bound and never manufactures a successful output value. These are Rust target contracts to preserve when dependency planning, type resolution, and task emission move to `flight-compiler`.

Symbol-keyed `EntityRuntimeKey` storage uses a generated native slot on every statically identified entity shape. Package-visible runtime extensions populate one typed aggregate handle; field-name/type collisions and nested structural identities use source-named typed slots inside that handle. Generic extensions use source-generated generic slot records stored by Rust `TypeId`; each concrete application is recovered through a checked `Any` downcast to an `Arc<Mutex<Slot>>`. Required fields that cannot be initialized honestly remain explicit `Option` slots until source initialization, so this representation introduces no opaque state, unsafe initialization, or observable default value. Entity aliases share slot presence. Object spread creates a fresh entity identity and native slot, copies the optional aggregate into that slot, and keeps any populated runtime handle shared. Runtime field mutation evaluates the receiver and value before acquiring the relevant lock once. A generic access without a statically recoverable concrete application remains a source-scoped blocker, as do receivers outside the statically closed entity family. Runtime alias parameters retain their Rust arity through zero-storage marker projections that normalize to the same handle.

Every promoted crate that emits entity fields or `FlightEntity` implementations must also emit or import the root `EntityRuntime`, `EntityRuntimeStorage`, and `FlightEntity` items. Generation enforces this invariant before writing the crate, and compile-backed emitter fixtures exercise promoted roots independently of the aggregate candidate workspace.

Entity runtime storage retains `Arc<Mutex<_>>` even though upstream execution is currently single-threaded. Generated callback objects are `Send + 'static`, the `FlightCallback` contract is `Clone + Send + 'static`, and callbacks may capture entities; `Rc<RefCell<_>>` and `Arc<RefCell<_>>` would make those captures non-`Send`. Runtime mutations therefore acquire one mutex only after receiver/value evaluation and keep the guard for the shortest practical scope. Lock cost still needs measurement in a regenerated native workload. Poisoning is not silently recovered: initialization checks should ultimately move outside guard lifetimes so an expected invariant panic cannot poison otherwise valid shared storage.

Package-wide exported-type catalogs drive discriminated open-interface discovery. A family is widened only when descendants explicitly redeclare `kind` and every widened member is safely default-materializable. This promotes the Light family without corrupting recursive trait hierarchies or callback-bearing families. Families that cannot satisfy that invariant need a tagged payload representation rather than unsafe zeroed/default storage.

The next cross-cutting tasks are Future/task lowering under the design checkpoint, typed backend-capability IR for dynamic host objects, and a tagged representation for non-defaultable open families.
